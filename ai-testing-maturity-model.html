📋 模型总览

AI 测试不是一步到位的"魔法"，而是一个从"人用 AI"到"AI 自治"的渐进演进过程。四个级别的本质区别在于：AI 在测试流程中的角色从"工具"逐步升级为"智能体"，从"被动响应"逐步进化为"主动自优化"。

每个级别的跃升，核心是回答一个问题：谁来驱动优化——是人来驱动 AI，还是 AI 自己驱动自己。随着级别提升，人从"操作者"逐步退后为"监督者和决策者"。

L0
Level 0：手工探索期
"每个人都在用，但没人管"

核心特征：测试同学以个人为单位，自发使用 ChatGPT、Claude 等通用大模型辅助测试工作。没有统一标准、没有流程约束、没有质量保障。

典型场景：某个测试同学在写用例前，把需求文档丢给 ChatGPT，让它帮忙列一些测试点；或者拿一段代码让 AI 帮忙分析逻辑。效果好不好完全取决于个人的 Prompt 技巧和对 AI 能力边界的理解。

⚠️ 存在的问题
  • 质量不可控：同一段需求，不同人用不同 Prompt 生成的用例质量差异巨大，没有基线对比
  • 知识不沉淀：每个人摸索出的好 Prompt、好实践都留在个人手里，团队换人就归零
  • 无法度量：AI 到底有没有帮助？帮了多少？没有任何数据支撑，管理层看不到 ROI
  • 安全隐患：把业务文档、代码直接丢给外部 AI 工具，存在数据泄露风险

这个阶段的价值：虽然问题多，但 Level 0 是不可跳过的。它让团队"先尝到甜头"，建立对 AI 测试的基本认知和信心。关键是不能停留在这一步。

L1
Level 1：流水线雏形期
"有了流水线，但每步都是孤岛" · 当前所处阶段

核心特征：AI 测试能力被集成为多阶段流水线（Pipeline），有明确的阶段划分和输入输出约束，但各阶段之间是"松耦合"的独立步骤，缺乏整体优化和反馈机制。

Phase 0 · 文档解析：通过"动词+obj"格式从需求文档中提取功能点（FP），扫描 Lion/MQ/Cache/Crane 等关键词建立中间件映射。采用 18 类信号扫描（文本 10 类、图表 5 类、结构 3 类）系统化提取信息，防止遗漏。每个功能点满足"原子性"——最小不可再分的功能单元。

Phase 1 · 三路并行：采用三路并行架构，互不阻塞，任何一路超时（300s）即降级跳过。

A 路 · 知识图谱
从已有知识图谱中检索与当前功能点相关的测试点和领域知识
B 路 · 专家经验
拉取经验知识库中的规则约束（experienceFlag=0 纯经验数据）
C 路 · 历史用例
从团队沉淀的历史用例库中检索相似场景的参考用例

Phase 2 · 用例生成：按优先级分层生成，产出标准 9 列用例格式。采用变更类型三分法（New/Enhanced/Config）精确控制中间件测试点生成粒度。

P0 主路径 — 核心功能正向流程
P1 边界与幂等性
P2 降级与补偿
P3 极端场景

Phase 3 · 质检交付：执行两层质检——第一层检查 P0 功能点覆盖率；第二层用 testcase-dedup-checker 做场景级语义去重。验证 9 列完整性与预期结果可验证性。最终通过 citadel 写入学城目录，后置数据上报异步执行。

🔴 Level 1 的关键问题
  • 流水线没有"学习能力"：Phase 2 生成用例时不知道 Phase 1 检索质量如何，Phase 3 的质检结果不会反馈给 Phase 2 改进。跑一千次都用同样的逻辑
  • Prompt 约束不够严格：用例质量波动大，缺乏版本管理和 AB 测试机制
  • 用例去重依赖人工：未实现自动 Embedding 相似度计算和去重
  • 领域知识不可复用：不同项目的知识没有形成可复用的知识库
  • 中间产物不可追溯：流水线的中间步骤产出无法回溯和审计
L1 → L2 过渡期关键建设项

1. 引入 Embedding 去重和 Step 1.5 质检层：在 Phase 1 和 Phase 2 之间增加一层质检，用向量相似度自动识别和合并重复用例，不再等到 Phase 3 人工处理。

2. 建立 Prompt 版本管理和 AB 测试机制：不同版本 Prompt 生成的用例质量可以量化对比，持续迭代优化。

3. 统一用例数据格式和接口规范：为后续数据反馈闭环打好基础——如果用例格式不统一，就无法做自动化的质量分析和反馈。

L2
Level 2：数据驱动期
"流水线会从执行结果中学习"

核心特征：流水线不再是"静态"的，而是建立了执行信号反馈闭环。用例生成后真正执行的结果会回流到生成阶段，驱动模型和策略的持续自优化。

🔄 核心能力 — 反馈闭环

执行信号回流到用例生成 Agent："低价值"用例的 Prompt 模式被降权，"发现缺陷"的模式被增强，"用例本身有问题"的类型加入黑名单。

🏗️ 需要的基础设施
  • 数据采集层：统一记录每条用例的执行结果、缺陷关联、审核意见，形成结构化的用例质量数据集
  • 信号分析层：对采集数据做统计分析，识别"哪些类型用例质量高""哪些 Prompt 模式产出低价值用例""哪些功能点覆盖经常遗漏"
  • 反馈应用层：将分析结论自动转化为生成策略调整 — Prompt 权重调整、知识图谱节点更新、历史用例优先级重排
📊 关键指标体系转变

成功指标不再是"生成了多少用例"或"用例数量减少了多少"，而是聚焦四个核心指标：

缺陷逃逸率
线上缺陷是否下降或持平，最核心的质量指标
用例有效性
过去半年抓到 bug 的用例占比，衡量用例实际价值
回归效率
全量执行时间是否缩短，衡量回归测试投入产出
测试设计人效
用例编写耗时是否降低，衡量设计环节的效率提升

核心逻辑：如果用例量减半但缺陷逃逸率上升，说明优化方向是错的。

✅ 组织阻力的缓解
  • 对执行层：有了数据反馈可以证明"AI 处理重复劳动，人专注探索性测试"，保留人工否决权
  • 对管理层：A/B 实验数据能说话（用例量降 40%+ 审核时间从 3 天降至半天）
  • 对研发层：Pipeline 输出可以稳定对接自动化框架，价值可量化
L3
Level 3：自治智能期
"Agent 自己决定怎么测"

核心特征：不再需要人工配置 Prompt 策略、选择知识源、设定生成优先级。Agent 能够根据项目特性自适应调整整个测试策略——包括决定测什么、不测什么、用什么方式测、测到什么程度。

⚡ 与 Level 2 的本质区别
  • Level 2 是"被动优化"：人分析数据，人调整策略，AI 只是执行
  • Level 3 是"主动自治"：Agent 自己分析反馈数据，自己调整策略，甚至自己决定是否需要补充新的知识源
🤖 典型场景

一个新需求进来后，Level 3 的 Agent 会自动完成以下全部工作：

  • 分析需求的变更类型和影响范围，自动判断需要走哪些测试路径
  • 根据该项目历史缺陷数据，自动调整测试优先级（如该项目幂等性问题多，自动加重幂等测试）
  • 自动选择最合适的知识源（不需要人配置走 A 路还是 B 路）
  • 发现现有知识不够时，主动触发知识补充流程
  • 生成用例后自动评估质量，不达标的部分自主重新生成
  • 把执行结果和缺陷信息自动关联到知识图谱，持续丰富团队知识资产
🔧 技术前提
  • Agent 自主决策能力：Orchestrator Pattern 的成熟形态，子 Agent 不仅能并行执行，还能自主编排
  • 知识图谱自演化能力：不需要人工维护，自动从执行数据中学习和更新
  • 多模态理解能力：不仅理解文本需求，还能理解 UI 设计稿、接口定义、代码变更等多种输入

🗺️ 演进路径实践建议

L0 → L1 把个人经验沉淀为团队流水线

遵循"先跑通闭环再工程化"原则，分四步走：

Phase 0 · 建立基线：统计 3 个已上线需求的手工用例数、耗时、缺陷情况

Phase 1 · 单点验证：回溯生成用例，与手工用例对比质量

Phase 2 · 小范围试点：选 1 个项目组真实运行

Phase 3 · 逐步推广：跑通后扩展到更多项目

最小可行方案仅为"一个优化 Prompt + 人工审核环节"，避免过早引入复杂架构。

团队阶段 MVP 策略 投入
初创团队 仅需 Step 2 Prompt 约束 半天
成熟团队 加 Embedding 去重 + Step 1.5 质检 1 周
大型团队 全套改造 + 反馈闭环 3-4 周
L1 → L2 建立数据反馈闭环（当前最关键）

1. 统一用例数据格式：让执行结果可采集、可分析

2. 建立用例质量指标体系：缺陷逃逸率、用例有效性、回归效率、测试设计人效

3. 在流水线中增加反馈接入点：让执行信号能回流到生成阶段

L2 → L3 从被动优化到主动自治（长期目标）

这一步跨度最大，技术上依赖 Agent 自主决策和知识图谱自演化的成熟。建议作为长期目标，在 Level 2 建设过程中有意识地预留扩展点：

• 知识图谱的更新接口预留

• Agent 编排的可配置化

• 多模态输入的接入预留
